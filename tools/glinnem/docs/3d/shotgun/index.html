Introduction to Shotgun

In order to start building a 3D game, you need to make a map environment first.

There are two ways to start making a map, you can:

  1. Make a new (or open an existing) 3D project in Glinnem, and select "Create map" in the actions panel. (Recommended)
  2. Open Shotgun.exe in your Glinnem bin directory, and follow the prompts.

If you already have a map loaded you can click "Edit map" in the same actions panel, or if you already have a compiled .gmf (Glinnem Map File) you can click "Load map" in the actions panel as well.

Commands

When launching Shotgun from Glinnem's bin directory, you get access to the command prompt before the main window opens, where you can either enter your project directory, or run commands that Shotgun will refer to after the main window opens.
Commands and their functions are listed below:

--prefdir [String] Replace [String] with the directory to your preferences.txt Loads your saved preferences from file. ✓

Usage

When you're in the editor, there is a simple toolbar at the top left of the screen. From there, you can insert primitive geometry, such as cubes, spheres, polygon-prisms, cylinders, flat triangles you can edit the vertices of, flat quadrilaterals you can edit the vertices of, and one more button to insert a .obj file as raw triangles or as one big object.

To swap between modes, you can press M to switch to the move tool, C to switch to the scale tool, and R to switch to the rotation tool.

Move Tool

To move geometry around the viewport, you can use the move tool by clicking on any piece of geometry with movement mode ON, and dragging the X, Y, or Z gizmo. Holding Shift while dragging moves in increments of 5 units.

Scale Tool

To scale geometry, you can use the scale tool by clicking on any piece of geometry with scale mode ON, and dragging one of the X, Y, or Z gizmo. Holding Shift while dragging scales in increments of 5 units. Holding Alt while dragging pivots from the opposite face you are scaling from.

Rotate Tool

To rotate geometry, you can use the rotate tool by clicking on any piece of geometry with rotate mode ON, and dragging the pitch, yaw, or roll gizmo. Holding Shift while dragging rotates in increments of 5°.

Light

Shotgun isn't exclusive to just geometry, it includes the ability to bake static lighting into your map. Since your map geometry isn't going to move, it saves processing power to pre-calculate all the lighting data before runtime in adjustable detail levels. Of course, this is optional.

Some properties like radius determine how far rays go until they stop, and strength indicates how sharp/soft shadows will appear based on its distance from the area light. There are three light objects you can place to control how light is baked. At least one of these types have to be placed somewhere in your map for the Bake lighting! option to be available.
These include:

Sun

A Sun is a light with no meaningful position in space. Instead, it represents a direction in the sky infinitely far away from the map. It is essentially a rotation that determines the direction the sunlight comes from.
The sunlight is represented by parallel light rays traveling towards the map, which produce sharp shadows.

Area Light

An area light is a light with adjustable radius, and strength, it casts light rays in all directions from the area light.

Spotlight

A spotlight casts light in a set direction, in a circle, or in any polygonal shape, with adjustable shape size, radius, and strength.

File Types

Shotgun and Glinnem share one file type for maps called a .gmf, or a "Glinnem Map File", containing your map and its lighting.
In a geometric sense, a .gmf contains raw triangle data grouped into type names such as cube, sphere, etc.
In a lighting sense, a .gmf contains a baked lightmap texture, with a second UV set that maps every static surface of the map to its corresponding area of the lightmap.
In a texture sense, a .gmf contains the textures assigned to its triangles, along with their UV coordinates within each group.
In a collision sense, a .gmf contains hitboxes of four different types; Floors, Walls, Ceilings, and Out Of Bounds. More on this on the next section.
Both programs read these files in different ways.
Below covers how Shotgun and Glinnem read these files.

Shotgun

Shotgun reads each group as it is, which is why instead of seeing raw triangles when editing a map, you see actual cubes. (Even though it obviously is still triangles, you edit a cube instead of setting each individual vertex of a triangle.)

Glinnem

Glinnem doesn't really care about the groups, it reads the raw triangles within them and displays them as static geometry. It also takes the UV and texture data (For both the light, and the decals), and applies them to every applicable surface.
Glinnem doesn't necessarily care about collision data when in editor mode, but it does matter in playtest mode -- So in order for Glinnem to open a .gmf, collision data needs to be present.

Collision

A valid .gmf to be read by Glinnem needs to contain a collision map, and one can be made by clicking the Calculate Collisions button in Shotgun's actions panel.
These are calculated via the normals of triangles, and are important to be understood when creating/troubleshooting maps, and writing custom movement systems.
Below covers the four different types, how they work, and how they are calculated, for simplicity they will be looked at from a 2D perspective. Also, when I refer to the "Player movement" I'm talking about the built in code for the player entity, that doesn't necessarily mean that if you edit that code, the player will behave the same way to collision objects.

Floors

triangles whose normals are facing upwards between angles 190° to 350° are classed as a floor triangle, and the collision extends 20 units downwards. When the player's feet touch the collision space, the player will snap to the surface of it.

Ceilings

triangles whose normals are facing downwards between angles 10° to 170° are classed as a ceiling triangle, the collision extends 20 units downwards, and infinitely upwards.
When the player hits a ceiling while moving upwards, they will be deducted of all upwards momentum, and movement for that frame will be cancelled.
When the player hits a ceiling while moving downwards, they will be deducted of all horizontal momentum, and all horizontal movement for that frame will be cancelled.
When the player hits a ceiling while moving on the ground, all movement for that frame will be cancelled.
i.e. I said that the ceiling goes infinitely upwards, but that's only when in isolation. which it should never be in, it goes upwards until it hits a wall, or a slanted floor.

Walls

triangles whose normals are facing horizontally between angles 170° to 190° (Remembering this is from a 2D perspective) are classed as a wall triangle, and the collision extends 20 units towards and behind the triangles normal vector.
When the player touches the collision space, the player will be pushed out of it in the normal's facing direction by the amount necessary to get it outside of the space, NOT by the same amount that the player was moving into it.

Out Of Bounds (OOB)

Out Of Bounds (OOB) collisions are unique in the sense that they don't need a parenting triangle to exist, in fact they exist in every single map, even if it doesn't have ANY triangles, however it is arguably the most important when it comes to troubleshooting your maps.

OOB is the default state of space that is not protected by collision geometry. It is not a floor underneath the map, and touching OOB does not automatically kill the player.

Floor, wall, and ceiling collision geometry defines areas of space where the player is allowed to move. Everything outside of those protected areas is considered OOB. OOB can extend vertically through the entire usable height of the map, rather than existing only underneath it.

For example, imagine a map made of several floating islands. Without a large floor collision surface underneath the islands, the empty space between them is OOB. The player therefore cannot simply jump from one island to another, because the collision system prevents the player from entering that unprotected space.

A large floor collision surface can instead be placed underneath the islands. This creates a safe area above the floor, allowing the player to move and jump freely between the islands. An invisible static entity can then be placed over the same area and given game logic that kills the player when they reach it. This creates a traditional "death barrier".

Importantly, OOB itself is not a death barrier. During normal movement, the collision system prevents the player from entering OOB. If the player is already inside OOB before movement checks begin, such as after being teleported there, the player will be detected as being outside of valid collision space and killed. This is not a game mechanic, or OOB giving a "void death" effect. It is a failsafe for the player being placed somewhere they are not supposed to be.

Tooltip: As previously stated, if you want a section of your map to function as a void that the player can fall into, you can create a death barrier (two floor triangles). Here's how:

You can add a large quad under your map in Shotgun to block the OOB, then add an invisible static object in Glinnem covering the same area for the death logic. Then script the static object like this: 

int main() //If you didn't read the scripting doc, the main function is an optional function for each object that runs once for every applicable object, unless called elsewhere.
{
  Player = game::player; // Make sure your player object's ID string is set to "player", or change this value to match with your player.
  Barrier = game::barrier; // Make sure this object's ID string is set to "barrier", or change this value to match with your player.
}

void EntityTickCheck() //If you didn't read the scripting doc, the EntityTickCheck function is an optional function for each object that runs every tick.
{
  if (Player:Collided(Barrier))
  {
    Player.Health = 0; // If your player object uses a different identifier, replace "Health" to match.
  }
}
